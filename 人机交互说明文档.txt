1. 硬件构成与系统拓扑
================================================================

1.1 系统连接结构（定稿）
----------------------------------------------------------------
┌─────────────┐  UART    ┌─────────┐   WiFi    ┌──────────────────┐
│  F板        │─────────>│ ESP8266 │──────────>│  ESP32-S3        │
│ STM32F407   │<─────────│(自写转发 │<──────────│  (HMI 主控)      │
│  USART2     │  PD5,PD6 │  程序)   │           │   ├─ ST7262 显示 │
└─────────────┘          └─────────┘           │   ├─ GT911 触摸  │
                                               │   └─ 状态机/协议 │
                                               └────────┬─────────┘
                                                        │ RGB并口/I2C
                                                        v
                                                   触摸显示屏

1.2 各芯片职责
----------------------------------------------------------------
F板         STM32F407VET6，协议实现(protocol.c)之一，
            经 USART2(PD5,PD6) 收发帧，波特率 115200。
ESP8266     F板的WiFi模块，运行【自写转发程序】（非AT透传），
            只做两件事：
              ① 把F板USART2发来的数据，经WiFi发给ESP32-S3；
              ② 把WiFi收到的数据，经串口发给F板。
            不解析协议帧，纯字节搬运——协议层归两端主控，
            搬运层归ESP8266，两层职责一刀切开，
            协议升级永远不碰ESP8266代码。
ESP32-S3    HMI主控，所有HMI计算都在这里：
            UI渲染、触摸处理、HMI状态机、协议组帧解析
            （protocol.c同源移植）、ACK重传计时。
ST7262      显示核心，RGB并行接口（S3的LCD外设驱动），
            时序参数按所选触摸屏规格书配置；
            UI框架建议 LVGL（S3双核带得动800x480）。
GT911       电容触摸核心，I2C接口（地址0x5D/0x14），
            INT+RST两根GPIO，中断/轮询读坐标均可。

1.3 ESP8266 为什么不用AT透传模式（设计论证，报告可用）
----------------------------------------------------------------
· AT透传的 +++ 转义序列坑：数据流中出现类似字节会被误判
  退出透传，链路意外断开；
· 透传缓冲区溢出后静默丢字节，无从察觉与恢复；
· 透传模式下收发节奏、缓冲水位完全不可控，
  出问题只能整套复位；
· 自写程序：缓冲、重连、错误恢复全部自己可控，
  出问题可打日志定位——这是"避免出错"的落点。

1.4 设计影响
----------------------------------------------------------------
· 帧协议零改动：转发程序不碰帧内容，帧结构/命令字/转义/
  ACK重传全部原样有效；
· WiFi链路有延迟抖动（几十ms级）且可能瞬断——
  重传超时取协议建议区间上限（500ms），
  重传机制必须可靠，不能当作"锦上添花"；
· 智能分布两端（F板STM32 / HMI的ESP32-S3），中间搬运层
  保持"哑"——系统里不存在第三个需要维护协议状态的节点，
  联调抓包只需看两端，转发层问题可隔离排查。

2. 模块角色与系统定位
================================================================
HMI 是用户与机器人系统的唯一交互入口：
- 上行（用户→系统）：录入取件码、启动任务、停止任务
- 下行（系统→用户）：任务进度反馈（前往中/已抓取/已送达）、
  故障显示、受阻提示与恢复
- 不参与导航决策、不参与取放控制，只做"下发意图 + 接收结果"

三端分工（写报告的职责划分素材）：
  HMI(ESP32-S3)  用户意图下发、进度/故障呈现
  F板(STM32F407) 导航、路径规划、机械臂执行
  H板(OpenMV)    识别、指挥取放动作
HMI 在整个任务中只在"阶段一"主动发起通信，
之后全程处于被动接收状态。

================================================================
3. 通信链路与命令子集
================================================================
链路全程：F板STM32F407 USART2(PD5,PD6)
          → ESP8266(自写转发程序)
          → WiFi → ESP32-S3(HMI主控)
波特率：115200（F板↔ESP8266段；ESP8266↔ESP32-S3为WiFi段）
帧头：0x5A；协议两端同源移植 protocol.c
      （F板端跑在STM32上，HMI端跑在ESP32-S3上，
       中间的ESP8266对协议完全透明）
重传超时：500ms（WiFi链路取协议区间上限，补偿延迟抖动）

HMI 使用的命令子集（完整定义见协议文档 4.1）：
  发送方向：
    0xFF TEST          连接测试（上电握手，原样回帧）
    0x10 CMD_CODE_INPUT 下发取件码（3字节ASCII）
    0x11 CMD_START      启动指令
    0x12 CMD_STOP       停止指令
    0x00 ACK            应答 F 板发来的命令
  接收方向：
    0xFF TEST           回原帧（上电握手）
    0x13 CMD_HMI_PICKED 已取到包裹
    0x14 CMD_HMI_DELIVERED 已送达
    0x15 CMD_ERROR      故障上报（1字节故障码，0x01~0x09）
    0x16 CMD_HMI_RESUME 受阻恢复通知
    0x00 ACK            F 板对 HMI 命令的应答

================================================================
4. 上电与链路建立
================================================================
    上电 --> F板发 TEST(0xFF) --> HMI 原样回 TEST --> 链路就绪
- F板是发起方，HMI 全程被动应答，不主动发起任何连接；
- 超时未回：F板按重传规则处理（500ms x 3 次）；
- 3 次重传后链路仍未建立：F板按0x07流程处置，
  HMI 显示"通信故障"，保持在待取件状态；
- 握手采用"原样回 TEST"而非 ACK 的理由：
  ① TEST回显与命令ACK语义分离（链路活着 vs 命令已执行）；
  ② F板可比对回显帧内容，多验证一层"链路能完整传帧"；
  ③ HMI 回显不需要任何状态判断，实现最简单。

================================================================
5. 两步操作流程（核心规则）
================================================================
用户操作拆成"确定"和"启动"两步，发送时机严格绑定在启动：

┌──────────┬────────────────────────────────────────────────┐
│ 用户动作 │ HMI 行为                                       │
├──────────┼────────────────────────────────────────────────┤
│ 触摸输入 │ 软键盘录入，本地暂存                           │
│ 取件码   │                                                │
│ 点击确定 │ 校验3位数字，本地保存并显示，不发送任何帧      │
│ 点击启动 │ ① 发 CMD_CODE_INPUT(取件码) → 等ACK            │
│          │ ② 发 CMD_START → 等ACK                         │
│          │ ③ 两个ACK都收到后，状态切"机器人前往中"        │
│          │ (任一命令重发3次无ACK → 显示通信故障，          │
│          │  保持待取件)                                   │
└──────────┴────────────────────────────────────────────────┘

设计要点（报告论述素材）：
· "确定"不发帧：避免用户误触/反复修改取件码时刷屏链路；
· 点击启动≠立即切状态：必须以收到 F 板 ACK 为准切换——
  状态切换凭据是回执，不是本地按键，杜绝
  "界面已显示前往中、实际命令没发到"的假状态；
· 这一点在 WiFi 链路上尤其重要：
  无线链路可能静默丢帧，本地凭空切状态风险比有线更大。

6. HMI 状态机（含受阻/恢复处理）
================================================================
（状态机在 ESP32-S3 内部维护）

用户触摸输入取件码 → 点击确定(本地保存，状态不变)
│
▼
┌───────────────┐
│    待取件     │
└───────────────┘
│ 点击启动 → 发CODE_INPUT+START
│ → 收到F板两个ACK
▼
┌───────────────┐
│ 机器人前往中  │ ←— ACK未到不切状态(3次重发无ACK显示故障)
└───────────────┘
│ 收到 CMD_HMI_PICKED 并回ACK
▼
┌────────────────┐
│ 已抓取到包裹   │
└────────────────┘
│ (机器人返航中，对HMI透明，状态保持)
│ 收到 CMD_HMI_DELIVERED 并回ACK
▼
┌───────────────┐
│   已送达      │ —→ 复位回到待取件，等待下一次任务
└───────────────┘

故障/恢复旁路（V1.4 修正，覆盖全部故障码 0x01~0x09）：
· 任意状态下收到 CMD_ERROR：
    - 故障码=0x08（前方受阻，可恢复型）：
      → 回ACK，显示"前方受阻，等待移障"
      → 状态机【不复位】——这是唯一不复位的故障码，
        任务仍在进行，障碍移除后原地续跑
    - 故障码=0x01~0x07、0x09（任务终止型）：
      → 回ACK，显示故障码，复位回待取件
· 收到 CMD_HMI_RESUME(0x16)：
    → 回ACK，清除"受阻"提示，恢复原状态显示
· 受阻期间用户点击停止：
    → 照常走 STOP 流程终止复位
     （车本来就在停车，无运动冲突）
· 任意状态下用户点击停止 → 发CMD_STOP(F回ACK)，复位回待取件。

7. 报文收发行为规范（ACK 规则）
================================================================

7.1 总规则（协议 V1.5 第六节）
----------------------------------------------------------------
· 凡是协议内定义的命令，收到一律回 ACK，无一例外；
· 重复帧同样回 ACK（幂等处理）——回 ACK 是为了止住
  发送方的重传；
· 唯一例外：协议外的未知命令码 → 丢弃不回
  （回ACK反而有害：发送方会误以为命令已被理解执行，
   把故障掩盖了）；
· ACK 只代表"收到并开始执行"，不代表"做完"——
  做完由各自事件帧接力（PICKED/DELIVERED/RESUME等）；
  一问一答两层：ACK管"你听到没"，事件帧管"你做完没"。

7.2 发送侧
----------------------------------------------------------------
- 所有发出的命令都要等 ACK，超时 500ms（WiFi链路取上限），
  原样重发 x3；
- 重发期间收到 ACK 立即停止重发；
- 3 次重发失败 → 置通信故障（见第8章）。

7.3 接收侧
----------------------------------------------------------------
- 收到事件类命令（PICKED/DELIVERED）→ 回 ACK → 更新状态机；
- 收到 ERROR(0x08) → 回 ACK → 显示受阻提示（不复位）；
- 收到 ERROR(0x01~0x07, 0x09) → 回 ACK → 显示故障码
  → 复位回待取件；
- 收到 0x16 → 回 ACK → 清受阻提示恢复显示；
- 收到重复帧 → 幂等处理：
  （如 PICKED 重发期间收到两帧，第一帧已切状态，
   第二帧回 ACK 即可，不重复显示/不清计时；
   重复的 ERROR(0x08) 直接回ACK，保持受阻显示不变）

================================================================
8. 异常处理
================================================================
场景                          处理
----------------------------------------------------------------
发出的命令3次重发无ACK        显示"通信故障"，状态复位回待取件
收到 CMD_ERROR(0x01~0x07,     回ACK，显示对应故障码含义，
0x09 终止型)                  复位回待取件
收到 CMD_ERROR(0x08 可恢复)   回ACK，显示"前方受阻，等待移障"，
                              状态机保持
收到 CMD_HMI_RESUME(0x16)     回ACK，清受阻提示恢复显示
用户点击停止                  发CMD_STOP，F板回ACK后复位回待取件
                              （ACK未到也先复位界面，F板侧
                               按重传规则自行兜底）
收到未知命令码                丢弃，不回ACK不报错（协议外帧）
WiFi瞬断后恢复                无需特殊处理：重传机制自动兜底，
                              F板重发3次内恢复则命令不丢
ESP8266转发程序异常           F板侧自写看门狗/重连逻辑兜底

故障码显示对照（与协议 V1.5 第五章一致）：
  0x01 电机驱动故障      0x02 舵机通信故障
  0x03 视觉搜索超时      0x04 抓取失败
  0x05 放包裹失败        0x06 路径规划失败
  0x07 串口通信超时      0x08 前方受阻(可恢复，不复位)
  0x09 超声波故障        ←— V1.4 新增

9. 界面显示要点
================================================================
- 取件码输入：触摸软键盘，仅 3 位数字，点击确定时校验
  （非3位/非数字拒绝保存并提示）；
- 状态显示区：与状态机状态一一对应
  （待取件/机器人前往中/已抓取到包裹/已送达）；
- 受阻提示态：显示"前方受阻，等待移障"（临时覆盖，
  收到 0x16 恢复原显示）；
- 故障显示：显示故障码 + 对应文字含义（含0x09）；
- 启动按钮点击后置灰，直到状态切换或故障复位，防重复提交。

11. 报告撰写建议
================================================================
可直接转画的图：
1. 系统连接图：F板↔ESP8266↔WiFi↔ESP32-S3↔ST7262/GT911，
   标注四层分工（第1章）
2. HMI 状态机图（第6章，一图讲清模块全部逻辑）
3. 两步操作时序图：确定(无帧)/启动(两帧两ACK)（第5章）
4. HMI 与 F板/用户的三方交互图（第2章职责划分）

值得强调的设计点：
- 状态切换凭据 = ACK 回执而非按键动作（可靠性设计）；
- "确定/启动"两步分离减少无效链路流量；
- 全部协议内命令统一 ACK + 重传 3 次判故障，
  通信闭环无盲发；
- 故障码二分类处理：终止型(0x01~0x07,0x09)复位、
  可恢复型(0x08)保持——HMI状态机与任务真实状态始终同步，
  不会出现"车在续跑、界面已复位"的脱钩；
- ESP8266 自写转发程序替代 AT 透传：规避 +++ 误断链、
  缓冲溢出静默丢字节、链路不可控三大坑，且不解析协议帧，
  协议升级与搬运层完全解耦（设计论证素材）；
- ESP8266 作为 F 板的WiFi外设而非独立智能节点：
  智能分布在两端（STM32/ESP32-S3），中间搬运层保持"哑"，
  系统里不存在第三个需要维护协议状态的节点；
- 分层清晰：协议层(F板STM32 + ESP32-S3) /
  搬运层(ESP8266) / 显示层(ST7262) / 交互层(GT911)，
  各司其职，便于分块调试。
