1. 系统概述
================================================================
机器人板上电后按固定流程自检初始化，然后进入
"待命 -> 取件 -> 返航 -> 放物"的循环工作模式。
人机交互端下发取件码与启动指令后，小车自主循迹前往取货点，
视觉模块通过串口B指挥完成取物；小车循迹返回原点后，
视觉模块再次指挥完成放物；之后回到待命，等待下一任务。

上电自检 -> 双链路握手(TEST) -> 电量检查 -> 舵机归位 -> 待命
  | (收到取件码+启动指令)
  v
路径规划 -> 循迹前往
  | 到达取货点 -> 视觉指挥取物(串口B,协议0xA5命令集)
  | 重新规划路径 -> 循迹返航
  | 到达原点 -> 视觉指挥放物(串口B)
  | 回到待命

2. 上电初始化阶段（严格顺序执行）
================================================================

2.1 双链路通信握手（第一件事，协议V1.5第六节第1条）
----------------------------------------------------------------
链路表（以协议V1.5为准）：
 串口A(USART2) 人机交互端 接收取件码、启动指令；汇报状态
 串口B(USART6) 视觉模块 握手确认在线；取放阶段接收动作指令

握手流程（TEST原样回显，非ACK）：
 上电 --> 串口A发 TEST(0xFF) --+（两路并发，互不等待）
        --> 串口B发 TEST(0xFF) --+
                                  v
        两路都收到TEST回显 --> LED常亮 --> 继续初始化
        任一路超时(500ms) --> 原样重发，最多3次
        3次无回显 --> LED闪烁（统一一种模式）--> 持续重试
- 串口A 3次失败：链路未建立，F板本地保持重试
  （HMI侧同时显示"通信故障"——双方各自呈现，规则同源）
- 串口B 3次失败：LED闪烁重试，不影响串口A链路
- 排查靠串口助手逐路看数据或查线

2.2 电池电量检查
----------------------------------------------------------------
- ADC 读电池电压换算电量（分压电阻比待电池型号定稿后确定）
- 低于阈值（暂定 20%）-> 蜂鸣器响 2 秒报警
- 报警后先按"继续工作"实现，策略接口留好
- 当前低电量不走协议上报（协议V1.5标注为预留项）

2.3 舵机归位
----------------------------------------------------------------
- 机械臂为 4自由度总线舵机，位置以 4 维坐标定义
 （每个关节一个目标角度，经USART3单向总线指令下发）
- 初始位置坐标（4个关节角数值待机械结构确定后填入）：
  #define SERVO_POS_HOME    {0,0,0,0}  /* 初始位置，占位 */
  #define SERVO_POS_GRAB    {0,0,0,0}  /* 抓取位置，占位 */
  #define SERVO_POS_RELEASE {0,0,0,0}  /* 放下位置，占位 */
- 注意：发送后无回传可确认，归位完成以固定时序保证

2.4 进入待命状态
----------------------------------------------------------------
- LED 常亮，串口A监听人机交互端指令

3. 场地地图与路径（H 结构）
================================================================
（本章 v0.6 内容经核对无误，v0.7 原样保留）

3.1 地图结构
----------------------------------------------------------------
实际拓扑为 H 形，1/2 是中间横杠与两根竖线的交点，
原点和三个取件点是 H 的四个端点，原点在右下：

 4 ------+   +-- 3
         |   |
 2 ------- 1     <- 中间横杠 1-2
         |   |
 5 ------+   +-- 0 (原点)

节点角色：
 0 原点（出入口，右下端点）
 1 纯路口（H 右交点，过点不停留）
 2 纯路口（H 左交点，过点不停留）
 3 取件点1（右上端点，货架1）
 4 取件点2（左上端点，货架2）
 5 取件点3（左下端点，货架3）

边（以行进方向描述）：
 0 -> 1 向上直行
 1 -> 3 继续直行向上（取件点1）
 1 -> 2 在 1 处左转，向左走横杠
 2 -> 4 在 2 处右转，向上（取件点2）
 2 -> 5 在 2 处左转，向下（取件点3）

边权重（graph_config.h，单位 cm）：
 0-1: 80   1-2: 70   1-3: 90   2-4: 90   2-5: 95

3.2 去程路径表（按取件码查表）
----------------------------------------------------------------
取件码  路径序列
 3      直行 -> 过点1 -> 直行 -> 到点3
 4      直行 -> 过点1 -> 1处左转 -> 过点2 -> 2处右转 -> 到点4
 5      直行 -> 过点1 -> 1处左转 -> 过点2 -> 2处左转 -> 到点5

3.3 返程路径表（回原点，按 H 几何推导，装车实测校验）
----------------------------------------------------------------
起点  路径序列
 3    掉头180° -> 过点1 -> 直行 -> 到原点0
 4    掉头180° -> 过点2 -> 2处左转 -> 过点1 -> 1处右转 -> 到原点0
 5    掉头180° -> 过点2 -> 2处右转 -> 过点1 -> 1处右转 -> 到原点0

推导依据：从 4 返程时车头朝上，掉头后朝下，过 2 时左转即朝向 1；
从 5 返程时车头朝下，掉头后朝上，过 2 时右转即朝向 1——
两者走横杠 2->1 后方向一致，所以在 1 处都是右转朝下回 0。

3.4 路径数据来源（双轨制）
----------------------------------------------------------------
- 运行时用 Dijkstra（path_planner 模块）出节点序列
- 用 3.2/3.3 的表出转角动作
- H 图上每条起终点路径唯一，Dijkstra 结果与手工表必然一致
- 以后改地图只改 graph_config.h，不改代码

4. 主工作循环（状态机）（v0.7 挂接协议命令）
================================================================
状态       触发条件        动作                    退出条件
----------------------------------------------------------------
STANDBY   上电完成/       串口A监听取件码+        收到有效指令
          一轮结束        启动指令
PLAN      收到指令        按取件码查3.2去程表     规划完成
                          （规划失败->上报0x06）
RUN_OUT   规划完成        循迹行驶+按表转角       到达取货点
                          (5.1/5.2；遇障->5.4冻结)
GRAB      到达取货点      串口B视觉指挥模式：     收到CMD_GRAB_DONE
                          收HANDOVER交权->        (0x20)
                          逐条执行坐标/爪指令
                          (5.5)
PLAN_BACK GRAB完成        查3.3返程表             规划完成
RUN_BACK  规划完成        循迹行驶+按表转角       到达原点
DROP      到达原点        串口B视觉指挥模式：     收到CMD_PLACE_DONE
                          收HANDOVER交权->        (0x21)
                          执行放物指令
                          ->回STANDBY
----------------------------------------------------------------
协议衔接细节（均见协议V1.5）：
- 进入GRAB/DROP：F板发 CMD_HANDOVER(0x01)，H板回ACK即交权；
- 动作指令：CMD_MOVE_COORD(0x10)/CLAW_CLOSE(0x11)/CLAW_OPEN(0x12)，
  每条F板回ACK后执行（逆运动学解算在F板完成）；
- 阶段完成：H板发 GRAB_DONE(0x20)/PLACE_DONE(0x21)，
  status=0成功/status=1失败——失败时F板向HMI上报
  ERROR(0x04/0x05)，任务终止；
- 取物成功后F板向HMI发PICKED(0x13)，放物成功后发DELIVERED(0x14)；
- GRAB/DROP阶段60s无指令 -> 报警兜底（参数待定）。

注：RUN_OUT / RUN_BACK 途中遇障碍时状态冻结（见5.4），
不跳出状态机，障碍移除后原地续跑。

5. 关键机制详细说明
================================================================

5.1 到点判定（循迹传感器）与行驶控制
----------------------------------------------------------------
- "到达一个点"的判据：四路寻迹传感器全部检测到黑线
- 行驶控制为双环结构：
  内环：编码器测速闭环（左右轮速度环）
  外环：循迹环（中间两路见线偏差 -> 差速修正，PID 待调）
- 四路全黑 -> 路径点计数 +1，对照路径表判断该点是
  "直行通过"、"在此转角"还是"到达"
- 电机驱动为 AT8236 双H桥：PWM 调速 + 方向控制，
  编码器脉冲同时用于测速与里程估算

5.2 原地旋转（MPU6050 + 编码器双方案）
----------------------------------------------------------------
1. 关闭循迹控制
2. 旋转角度检测主方案：MPU6050 yaw 角
   （DMP/软件积分待定），按路径表转角
   （左转90°/右转90°/掉头180°）旋转
3. 校验方案：左右轮编码器脉冲差
   （两轮转速差积分推转角，防打滑时与 IMU 互为校验；
   主用哪个、校验到什么程度，装车后定）
4. 进入 ±3° 容差带 -> 停止
5. 恢复循迹，缓慢直行重新找线后继续
   （找线直行可用编码器定距，超距未压线 -> 报警）
注：H 结构所有转角只有 90° 和 180° 两种，
旋转控制只需标定两个角度目标。

5.3 串口使用原则（状态门控分发 + 权力交接制的对应关系）
----------------------------------------------------------------
核心认知：串口是全双工两条线（TX/RX），物理上不存在"抢线"。
跨板的指令时序由协议的"权力交接制"约定（谁持权谁发话）；
板内的解析干扰用"状态门控分发"解决——两者不矛盾：
交接是跨板语义，门控是板内实现。

串口A（人机交互，帧头0x5A）：
- 无需仲裁——HMI只在初始下发取件码/启动/停止，
  之后F板主动汇报（PICKED/DELIVERED/ERROR/RESUME），
  HMI对F板发来的每条命令回ACK；
- 统一入口：组帧/解析/转义/重传全部走 protocol.c，
  与串口B共用同一份代码。

串口B（视觉，帧头0xA5）：
- 接收数据统一进 protocol.c 解析，按状态机状态分派：

  串口B收到帧
    |-- 状态=GRAB/DROP(已交权) -> 解析坐标/爪/完成帧，
    |                            交动作执行模块(5.5)
    |-- 状态=STANDBY等(未交权) -> 仅处理TEST/链路维持帧，
    |                            动作指令丢弃（未持权）
    +-- 未知命令码 -> 丢弃不回ACK（协议规定）

- 收到 CMD_HANDOVER -> 回ACK -> 门控切到对应分支；
- 收到 GRAB_DONE(0x20) status=0 -> 回ACK -> 状态机切PLAN_BACK
  -> 向HMI发PICKED；status=1 -> 回ACK -> 上报ERROR(0x04)终止；
- 收到 PLACE_DONE(0x21) status=0 -> 回ACK -> 回STANDBY
  -> 向HMI发DELIVERED；status=1 -> 回ACK -> 上报ERROR(0x05)终止；
- 兜底超时：GRAB/DROP 阶段 60s 无指令 -> 报警（参数待定）。
- 实现建议：收口为一个函数 uart_b_dispatch()。

5.4 障碍处理（最终版：停车上报人工移障，v0.7 接入协议帧）
----------------------------------------------------------------
方案演进记录：曾考虑 Dijkstra 重规划避障 -> 物理绕行编排
（逐步精简到无倒车四段动作）-> 最终因车体大转弯困难、
简化收益高，定为"停车上报、等人移障"。

策略（协议V1.5第七章障碍分支）：
 循迹行驶中
   v
 超声波测距 < 30cm -> 停车，关电机，LED闪烁提示
   v
 F板 -> HMI : CMD_ERROR(0x08)，HMI回ACK
   （重传规则照常：500ms x 3，失败按0x07流程但车保持停车）
   v
 （障碍物被移开后）
   v
 连续 5 次(间隔200ms)测距 >= 30cm -> 视为稳定恢复
   v
 F板 -> HMI : CMD_HMI_RESUME(0x16)，HMI回ACK
   v
 自动恢复循迹，节点计数不变，继续原路径

超声波异常分支（协议V1.5故障码0x09）：
- ECHO 一直不回落（无反射/传感器故障）-> 视为"测距无效"，
  不触发0x08（宁可靠近一点也不能误停死在路上）；
- 连续无效超限 -> F板 -> HMI : CMD_ERROR(0x09)，任务终止。

要点：
- 状态机冻结在当前状态（RUN_OUT/RUN_BACK），不是中止任务——
  障碍移开后原地续跑（0x08是唯一不复位的故障码）；
- 恢复条件"连续5次测距达标"防障碍被挪一半又放回的抖动误判；
- 人工移障是预期路径，不需要超时报警兜底；
- 障碍时车辆不动，图状态无需运行时修改，
  path_planner 的 BlockEdge/Replan 等运行时避障接口已删除。

HSRC04 测距实现时序：
- TRIG 给 >=10us 高脉冲，ECHO 高电平宽度换算距离
- ECHO 用 TIM 输入捕获测脉宽（或外部中断+定时器计数），
  不在任务里死等，避免阻塞与调度抖动影响
- ECHO 超时保护：见上"超声波异常分支"

参数：
#define OBS_TRIG_DIST_CM  30.0f  /* 触发距离，待实测确认 */
#define OBS_RESUME_CNT    5      /* 恢复判定连续次数 */
#define OBS_RESUME_MS     200    /* 恢复判定采样间隔 */

5.5 舵机动作（4自由度总线舵机机械臂，v0.7 删除回读表述）
----------------------------------------------------------------
- 机械臂为 4自由度总线舵机，经 USART3(PB10 TX) 单向总线控制，
  不占用 PWM 定时器资源
- 【重要】USART3 仅 TX 单向，F板收不到舵机回传——
  动作是否到位由视觉模块自行判断（视觉观察/时序控制），
  这是协议V1.5的明确设计（v0.6"自带位置回读"表述已删除）
- 位置一律以 4 维坐标定义（初始/抓取/放下，见 2.3 占位宏）
- 视觉下发的坐标命令（CMD_MOVE_COORD，x/y/z三轴，
  每轴符号+幅值2字节）统一进同一套换算链：
  视觉坐标 -> 逆运动学解算 -> 4个关节目标角 -> 总线指令下发
- 执行流程：收到H板指令 -> 回ACK -> 解算执行 ->（无回传确认）
  视觉模块自行判断到位后发下一条指令
- 舵机无响应/驱动异常 -> 检测后上报 ERROR(0x02)
- 建议独立 arm_task（或挂在串口收发上），与行驶控制互不阻塞
